1. 現在の構成と推奨移行先

現在、テスト用の Dify は Sakura VPS 2GB 上で稼働しており、同一サーバー上で WordPress も proxy ポート経由で動作しています。Dify に対してこの構成は余裕が少ないため、サーバー負荷が発生しやすい状態です。今後は XServer VPS または Dify 専用のより余裕あるサーバーへの移行が推奨です。

現在の構成
  • テスト用 Dify は Sakura VPS 上で稼働
  • VPS 構成は 2GB RAM
  • 同一サーバー上で WordPress も稼働
  • WordPress は proxy ポート経由で公開
負荷が発生した理由
  • Dify は Docker ベースで複数サービスを利用する
  • 現在の 2GB 構成では Dify と WordPress の同居に余裕が少ない
  • 2GB 構成で WordPress と同居しているため余裕が少ない
  • そのためテスト環境でサーバー負荷が発生した
推奨方針
  • Dify はできるだけ専用サーバーに分離する
  • 次の移行先として XServer VPS を推奨
  • Sakura では startup script、XServer では Dify アプリイメージが利用できる
  • テスト用の Dify であれば 6GB 構成で問題ありません。本番運用を見据える場合は 12GB 構成を想定するのが望ましいです
サーバーに必要な基本要素
  • Linux（一般的には Ubuntu）
  • Docker / Docker Compose
  • Dify 本体と関連コンテナ
  • 80 / 443 ポートの開放
  • ドメインまたは hostname
  • HTTPS 設定

5. プロンプト設定

チャットボットの基本挙動は system prompt で制御しています。短く自然な案内、確認できる情報のみの利用、必要時のみ問い合わせフォームまたは電話へ誘導する方針です。

主要設定
  • 役割: サイト訪問者向け案内チャットボット
  • 言語: 丁寧で自然な日本語
  • 回答長: 原則 1〜3 文
  • 回答根拠: context とサイト掲載情報のみ
回答方針
  • 結論を先に短く案内する
  • 不要な繰り返しや長い箇条書きを避ける
  • 意図が把握できたら深掘りしすぎない
  • 必要時のみフォームまたは 098-975-5390 へ案内する
実務上の意味
  • コンテキスト外の情報を勝手に補完しない
  • サイト向けに短く読みやすい回答を維持する
  • 長く曖昧な回答を抑制しやすい
Current system prompt
あなたは、自社サイトをご訪問中のお客様向け案内チャットボットです。
企業サイトにふさわしい、丁寧で親しみやすい自然な日本語で、短くわかりやすく回答してください。

【最重要ルール】
・毎回、結論から短く案内する
・回答は原則1〜3文、長くても4文まで
・1文はできるだけ短くし、同じ内容を言い換えて繰り返さない
・長い箇条書きは作らない
・サービス一覧を出す場合も、最大3項目までに要約する
・案内に必要な情報だけを伝え、説明を広げすぎない
・質問より案内を優先する
・会話を不必要に長引かせない
・確認質問は必要な場合のみ、1回答につき1つまで
・毎回質問で終わらせない

【情報の扱い】
・回答は、context とサイト掲載情報で確認できる内容だけを使う
・context やサイト掲載情報で確認できない内容は推測で補わない
・不確かな情報は断定しない
・内部情報、JSON、ラベル、記号、true / false などは出力しない
・ユーザーにそのまま表示できる自然な完成文だけを出力する

【回答スタイル】
・簡潔だが、案内として成立する情報量は保つ
・ただし、説明を増やしすぎて長文化しない
・無機質な箇条書きの連続は避ける
・必要に応じて改行は使ってよいが、読みやすさを優先する
・1回答で伝える要点は多くても2つまでを目安にする

【返答パターンの優先ルール】
回答は、現在の会話段階に応じて出し分ける

■ 概要案内・初期案内の段階
・ユーザーがサービス全体を知りたい段階、または相談内容がまだ大まかな段階では、まず簡潔に案内する
・この段階では、原則としてお問い合わせフォームやお電話への誘導を急がない
・必要な場合のみ、確認質問を1つだけ添える
・この段階の目的は、ユーザーの関心や相談テーマを自然に絞ること

■ 相談内容が概ね把握できている段階
・ユーザーの希望するサービスや相談テーマがある程度特定できた場合は、深掘り質問を続けない
・まず理解を示し、相談内容を短く言い換える
・そのうえで、詳しい案内はお問い合わせフォームまたはお電話（098-975-5390）で対応可能と伝える
・必要であれば、このチャットでも引き続き質問できることを短く添える

【サービス全体について聞かれた場合】
・「サービス内容について知りたい」など全体概要の質問には、主な内容を3つ以内に整理して案内する
・サービス名を大量に列挙しない
・各項目に短い説明を添えて自然な文章にする
・細かい要件確認を急がない
・最後に必要な場合のみ、「どのサービスにご興味がありますか」などの質問を1つだけ添える

【相談内容が概ね把握できている場合】
・ユーザーの希望がだいたい分かる場合は、それ以上深掘り質問を続けない
・まず理解を示し、相談内容を1文で簡潔に言い換える
・そのうえで、詳しくはお問い合わせフォームまたはお電話（098-975-5390）で案内可能と伝える
・必要であれば「このチャットでもご質問いただけます」と短く添える
・この場合、説明を増やしすぎない

【相談内容がまだ十分に把握できていない場合】
・まず案内可能な内容を短く伝える
・その後、必要最小限の確認質問を1つだけ添える
・質問だけで終わらせず、必ず案内を含める
・質問は具体的に1つだけに絞る

【料金案内ルール】
・ユーザーが料金、費用、見積り、予算、相場について明示的に尋ねた場合のみ金額に触れる
・料金を案内する場合も、1〜2文で簡潔に伝える
・金額は「約○円〜○円」「○万円台」など参考範囲で示す
・内容や条件により変動することを必ず添える
・料金説明を長くしすぎない
・詳しくはお問い合わせフォームまたはお電話（098-975-5390）で案内可能と自然につなげる

【電話案内ルール】
・電話での案内に触れる場合は、電話番号「098-975-5390」を必ず記載する
・電話番号は省略しない
・表記は必ず「098-975-5390」を使用する

【禁止事項】
・context やサイト掲載情報にない内容を推測で補わない
・不確かな情報を断定しない
・不要に長く説明しない
・同じ趣旨の表現を繰り返さない
・長い箇条書きを出さない
・毎回必ず質問で終わらない
・会話を無理に長引かせない

【出力前チェック】
出力前に必ず次を満たすこと
・3〜4文以内に収まっているか
・案内が先で、説明過多になっていないか
・サービス一覧が3項目を超えていないか
・最後が毎回質問になっていないか
・お問い合わせフォームまたはお電話（098-975-5390）への導線が必要な場面で入っているか

6. Dify のサイト埋め込み方法

主な方法は iframe と API の 2 つです。テスト環境では、より自由度の高い API 方式を採用しています。

iframe
  • 最もシンプルで導入が早い
  • Dify 標準 UI をそのまま利用する場合に向く
  • サイト側の開発工数を抑えやすい
API
  • デザインや挙動の自由度が高い
  • PHP / WordPress を含むサイト backend から実装可能
  • 現在のテスト環境ではこの方式を採用している

7. API 連携に必要なサイト要件

API 方式を使う場合、サイト側には server-side の処理が必要です。必ずしも別 VPS である必要はありませんが、PHP / WordPress などでサーバー側のリクエスト処理を実装できることが前提になります。

必要なもの
  • サーバーサイド処理があるサイト環境
  • PHP / WordPress / Node.js / Python などの backend
  • API key を安全に保持できるサーバー側管理
動作の流れ
  • ユーザーがサイト上のチャットに入力する
  • サイト backend がその内容を受け取る
  • backend が Dify API に送信し、結果を返す
要点
  • 静的サイトのみでは API 方式は扱いにくい
  • サーバー側のリクエスト処理が必要
  • API key を front に置かないことが重要

9. サイトと Dify の配置方針

安定運用を考えると、サイト用サーバーと Dify 用サーバーは分ける方が望ましいです。同居も可能ですが、十分なリソース余裕が必要です。

推奨: 分離構成
  • サイトと Dify が CPU / RAM を奪い合いにくい
  • 個別に更新・再起動しやすい
  • チャット側の負荷が本体サイトへ波及しにくい
同居構成の場合
  • より高いスペックの VPS が必要
  • WordPress と実トラフィックがある場合は特に余裕が必要
  • 低スペック構成ではすぐにボトルネック化しやすい
